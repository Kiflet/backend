# AGENTS.md

## Project

Kiflet: offline-first shipment tracking and proof of delivery for Ethiopian
trucking companies. See `README.md` for what it does and how it fits together.

This is **Kiflet/backend**, one of three repositories in the
[Kiflet](https://github.com/Kiflet) organization, with
[Kiflet/web](https://github.com/Kiflet/web) (Next.js) and
[Kiflet/mobile](https://github.com/Kiflet/mobile) (the Expo driver app).
Until `docs/migration.md` has moved them, this repository still renders
the dashboard, the public pages and the driver PWA. The Go module is
`github.com/kiflet/backend`.

- `docs/functional_requirements.md`: the original requirements (FR numbers
  are referenced in code comments). Appendix D records where the product
  deliberately differs; add to it when you depart from a requirement.
- `docs/logistics.md`: background on the problem
- `docs/E2E_TEST_GUIDE.md`: manual walkthrough of every flow
- `docs/deploy.md`: production, backups, staging, connecting the providers
- `docs/audit-2026-11.md`: the audit of November 2026 and its fix record
- `docs/audit-2026-11-19.md`: the audit of 19 November 2026 (the data,
  the flows, the API, the tests), which revised the plan, and its fix
  record
- `docs/architecture.md`: the target architecture (backend modules,
  RabbitMQ, Redis, the Next.js web and Expo driver apps, deployment)
- `docs/migration.md`: the phased plan from this codebase to that one,
  backend first: the data and the flows (phase 1), one API and its
  contract (phase 2), the driver's part of it with Kiflet/mobile (phase 3),
  the web's with Kiflet/web (phase 4). Until a phase is done, the
  Architecture section below describes what is running.
- `CONTRIBUTING.md`: these rules at full length
- `ROADMAP.md`: what comes next, in order. Delete a section once it is done.
- `CHANGELOG.md`: what changed in each release. It is the only file that
  may name what the product was called before; CI checks.

## Architecture

One Go application. It serves the dispatcher dashboard
(server-rendered `html/template`), the public tracking pages, the driver PWA
(`internal/web/static/driver`) and its JSON API, and runs the background jobs.
A process may run only some of that (`config.Roles`: web, worker,
scheduler, relay; `internal/app` wires each), so background work must not
assume it shares a process with the request that queued it: wake it
through `core.wakeWorkers` or a queue.
Kiflet/web and Kiflet/mobile will take over the pages and the driver app
(`docs/migration.md`, phases 3 and 4). Until then the pages and the PWA
are **frozen**: they get fixes, and only what the pilot needs. A new
feature is an operation of the API (`/api/v1`, `docs/architecture.md`,
section 11), not a page. Earlier Next.js and Expo apps were retired
before November 2026 and live only in git history; the new ones start from
the plan, not from those.

- `internal/app`: builds the app from its settings (providers, services, web
  server, background workers). `cmd/server` and the integration tests both
  use it, so new wiring goes here, not in `main.go`.
- `internal/web`: routes (`server.go`), middleware, handlers (`app_*.go`,
  `public.go`, `api_driver.go`, `api_public.go`), templates and static files
- `internal/modules/<name>`: the modules of `docs/architecture.md`
  (section 4), moving out of `internal/service` one at a time, each as its
  part of the API is built (`docs/migration.md`, section 5). A module owns its tables: `<name>.go`
  is its interface, `app/` implements it, `store/` is its sqlc package
  (queries in `store/queries/`, an entry each in `sqlc/sqlc.yaml`).
  Others call it only through the interface, and a write within another
  module's transaction takes that transaction as a `database.Conn`
  (`internal/platform/database`; from `internal/service`, `q.Conn()`).
  `internal/modules/boundaries_test.go` checks what each imports: the
  platform packages, `pkg/`, its own packages and other modules' root
  packages, never `internal/service`, `db` or `model`. Errors a person
  can act on are `internal/platform/apperror`'s (`service.Error` is the
  same type). Moved so far: audit, tenancy, identity, fleet, and
  shipments' tables, rules, documents and charges, and its history,
  which `shipments.History.Record` writes and publishes on the bus as
  `shipment.<type>` (booking, assigning and status changes still in
  `internal/service`).
- `internal/service`: the business rules not yet in a module. Handlers
  stay thin.
- `internal/model`: plans and prices, and aliases of what moved to the
  modules' `domain` packages (statuses, transitions and reasons to
  `shipments/domain`, roles to `identity/domain`)
- `internal/platform`: packages without business rules: `config`, `geo`,
  `phone`, `database`, `apperror`, and `text`, the words customers read, in English
  (`en.go`) and Amharic (`am.go`)
- `internal/db` and each module's `store/`: generated by sqlc from
  `sqlc/queries` and the modules' `store/queries`. Don't edit by hand
  (`internal/db/conn.go` is the one file that isn't generated); run
  `make sqlc`. sqlc leaves the output of a queries file that has gone:
  delete it too (CI checks).
- `internal/sandbox`, `cmd/sandbox`: the provider sandbox, a separate service
  playing Ethio telecom, telebirr and CBE Birr for the real adapters
  (`make sandbox`, `make run-sandbox`)
- `migrations`: goose migrations, embedded and applied on start
- `internal/platform/events`: the bus. A change others react to is
  published as an event in its transaction; subscribers run `Within` it
  (their writes commit with the change) or `After` it commits (live
  updates, waking workers). With RabbitMQ, each event is also written to
  `event_outbox`, and `internal/app/relay.go` publishes it.
- `pkg/broker`: RabbitMQ (exchanges, queues, confirms, retries). The app
  works without RabbitMQ (`RABBITMQ_URL` empty), so keep that path working.

## Working on it

Run commands from the repository root.

```bash
make db && make seed && make run   # http://localhost:8080, demo logins in README
make test                          # unit tests
make test-integration              # HTTP-level tests against PostGIS
make staging-up && make test-e2e   # production's images and compose file, over HTTPS
make vet
make lint                          # golangci-lint, node --check, gitleaks over the history
```

- Templates are reloaded from disk with `DEV_RELOAD=true` (`make run` sets it),
  but template errors only show at render time. `go test ./internal/web/`
  parses every page.
- The CSP is `script-src 'self'`, so no inline scripts. Pass data to JS through
  `<script type="application/json">` blocks or `data-` attributes.
- Every query is scoped by tenant. Keep it that way in new queries; one
  that is global on purpose says why on the line after its name
  (`-- tenant: none, <reason>`); `TestEveryQueryIsScopedByTenant`
  (`sqlc/`) fails on one that doesn't. A reference from one company's table to
  another includes the company: `(tenant_id, x_id) REFERENCES x
  (tenant_id, id)`, and a `SET NULL` names its column.
  `TestReferencesCarryTheTenant` checks every reference; the few an
  operator makes across companies are listed there with the reason.
- A Go page, or the PWA, is deleted only once the flows its tests cover
  are tested through the modules and the API (`docs/migration.md`,
  section 8): a module's rules by unit tests, its queries by store tests
  with another company's IDs, each operation by API tests.
- What a customer reads (their texts, the tracking and confirmation pages)
  comes from `internal/platform/text`, in English and Amharic: add the words to
  `en.go` and `am.go`, and use `{{.T "key"}}` in the template. Tests check
  that the two files match and that templates name only keys that exist.
- Metrics live in `pkg/metrics`. Label them by route pattern or another short
  fixed list, never by company, user or shipment ID.
- `audit_logs` and `shipment_events` are append-only: a trigger rejects
  UPDATE, DELETE and TRUNCATE. Code that must remove them (company deletion,
  retention) runs inside `purgeTx` in `internal/service/data.go`, which sets
  `kiflet.purge` for its transaction only.
- The public API (`api_public.go`) acts as its key's `service.Actor`
  through the same services as the dashboard; it has no rules of its own.
  `static/openapi.json` describes it, and `TestOpenAPIMatchesTheAPI` checks
  that the two have the same routes and fields: change them together.
- Webhooks subscribe to `shipment.*` on the bus and are written with the
  shipment's history: a new kind of event reaches them by adding it to
  `webhookTypes` in `internal/service/webhooks.go`. Their payload is the
  API's `ShipmentJSON` and `EventJSON` (`internal/service/api_json.go`).
- The driver app's status rules come from `/api/v1/driver/config`, which is
  derived from `AllowedTransitions` in `internal/modules/shipments/domain`.
  Change the rules there, not in JS.
- The driver app is ES modules with no build step. `app.js` starts it;
  what several modules change lives in `S` (`state.js`), since a module
  can't assign to another's variables. A new module needs a
  `<link rel="modulepreload">` in `driver/index.html`; `TestDriverBuild`
  checks.
- The driver app's service worker installs every file under
  `static/driver` as one version, listed in `/driver/build.json`
  (`internal/web/driver.go`), so a new file needs no list there. A deploy
  reaches a phone the next time the app starts after downloading it.
- The app may run as several instances (`APP_REPLICAS`). Keep state that
  must be shared in Postgres, not in memory: live updates already cross
  instances through RabbitMQ's `kiflet.live` (`internal/app/queues.go`)
  or, without it, `LISTEN`/`NOTIFY` (`internal/app/live.go`), and the
  rate limits are counted in Redis (`internal/web/limits.go`) or, without
  it, hold because Caddy keeps a client address on one instance.
- Live updates: an element with `data-live-region` and an `id` is fetched
  again and swapped in when a WebSocket message says something changed
  (`static/app.js`). Mark new live parts of a page that way instead of
  rendering them in JS.
- The look is the "Desk" design (light) and "Night" (dark mode): colours
  are tokens at the top of `static/app.css`, and soft tints and status
  colours are derived from them. Icons are lucide's: `{{icon "truck"}}`,
  from the names in `internal/web/icons.go` (copy a new one in from
  lucide-static). Fonts live in `static/fonts`, named with their version
  because they are cached for good.
- Page stylesheets (the `head` block, e.g. Leaflet's) load before `app.css`,
  so `app.css` can restyle vendor widgets.
- The sandbox imports only the standard library and `pkg/console` (a test
  enforces it): it implements the providers' side of each contract on its
  own. When a contract changes or is confirmed with a provider, change the
  adapter (`pkg/sms`, `pkg/payments`) and the sandbox together, and run
  `make test-integration`, whose sandbox tests run the adapters against it.
- Staging is `deployments/docker-compose.prod.yml` with
  `deployments/staging/compose.yml` on top, which only swaps in stand-ins for
  the outside world (the sandbox, Mailpit, SeaweedFS, Caddy's own CA). Change
  production's file and staging follows. `tests/e2e` runs against it; its
  last test restores a backup over staging's data.
- The Dockerfile and CI (`.github/workflows/ci.yml`) name the same Go
  release, the newest: change them together.
