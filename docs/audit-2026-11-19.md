# Kiflet audit, 19 November 2026

An audit of the backend before the move to three codebases goes further:
the shape of the code, its data and flows, its tests, and what Kiflet/web
and Kiflet/mobile need from it. It led to the revised plan in
`docs/migration.md`.

- **Date:** 2026-11-19
- **Commit audited:** `dcd7225` on `main`. Kiflet/web and Kiflet/mobile
  at their plans (documents only; neither has code yet).
- **Method:** reading the code, the schema, every query, the tests, CI and
  the deployment files; coverage measured from the unit and integration
  suites; the clients' architecture, design and migration documents read
  for what they ask of the backend. See [Scope and method](#scope-and-method).
- **Brief:** backend first. The data and the flows matter most; the web
  and mobile apps are adjusted to fit the backend, not the other way round.

`docs/audit-2026-11.md` is a different audit, of the product's behaviour,
with IDs of its own (`R1`, `S5`, `O6`…). This one's IDs are `D` (data and
flow), `A` (the API), `P` (privacy), `T` (tests) and `G` (process and
operations). When a finding is fixed, its row in the fix record gets the
pull request; the finding stays, as a record.

## Verdict

A careful, well-tested, pre-production Go monolith, a third of the way
through its reorganisation into modules. Its strength is the integration
suite, which runs against real Postgres, RabbitMQ, Redis, Garage and the
provider sandbox. Its weaknesses are in four places:

- **Data and the sync:** a few correctness gaps, cheap to fix while no
  company's data is in it, expensive after the pilot.
- **Tests:** the rules are tested almost only through whole HTTP requests,
  and mostly through pages that are going to be deleted.
- **The contract:** the API the two clients are planned against doesn't
  exist yet, nor do the conventions they assume.
- **Process:** nothing stopped a red build reaching `main`, and nothing is
  published for the clients to test against.

## Decided on 2026-11-19

1. **One versioned API.** `/api/v1` serves Kiflet/web with its session,
   companies' systems with API keys, and Kiflet/mobile under
   `/api/v1/driver/*` with its token. There is no separate `/api/web` or
   `/api/driver`. `docs/architecture.md`, section 11.
2. **Backend first, in this order:** the data and the flow; the API and
   its contract; the driver API, because Kiflet/mobile goes first; then
   the web's API, a wave ahead of Kiflet/web. Each module still in
   `internal/service` moves when its part of the API is built.
   `docs/migration.md`, section 6.
3. **The sync protocol changes** to a change feed per driver with an
   opaque cursor, sending only what changed. The driver app keeps its own
   SQLite database with most of its data on the phone, so this feed is
   what keeps the phone right. `docs/architecture.md`, section 11.
4. **The Go pages and the driver PWA are frozen:** fixes, and only what
   the pilot needs. The backend ends serving no pages.
5. **Where the documents disagreed:** no CSRF tokens (Go's cross-origin
   check on every request the session cookie authenticates); numbered
   pages with totals, and a cursor only for endless feeds; the driver's
   paths stay under `/api/v1/driver`.
6. **Branch protection** on all three repositories, and private
   vulnerability reporting on, as `SECURITY.md` promises.

## Data and flow

### D1. The sync can miss changes, and resends a week of loads every time

**High.** `internal/service/sync.go:493–496`.

The cursor a sync returns is the server's clock minus 5 seconds, and the
next sync asks for what changed after it. Rows are stamped with `NOW()`,
which in Postgres is the moment their *transaction began*. A transaction
that began before a sync and committed after it carries a stamp behind the
cursor the phone now holds, so that phone never receives the change. Any
transaction that runs longer than 5 seconds (a lock wait, a slow import, a
burst) can do it. What can be lost: office messages, broadcasts,
cancellation notices, and the removal of a load taken off the driver.

Loads themselves are not lost, only because every sync sends all the
driver's active loads and every load that changed in the last 7 days,
whole. At 20,000 drivers syncing every minute, that is the same data
downloaded again and again, on drivers' prepaid data.

**Fix:** a sequence per driver, taken under a lock in the same
transaction as each change, so the entries become visible in order and a
reader can never skip one; the sync sends only what changed
(`docs/architecture.md`, section 11, "The driver sync").

### D2. The database lets one company's rows point at another's

**Medium.** None of the 46 foreign keys between company-owned tables
includes `tenant_id`; only the Go code keeps a shipment's driver, vehicle
or document inside its company. Row-level security is not there yet
either. One forgotten check in a handler would link companies' data, and
nothing below it would refuse.

**Fix:** `UNIQUE (tenant_id, id)` on each parent table and every reference
as `(tenant_id, x_id) REFERENCES x (tenant_id, id)`; a store test that runs
each query with another company's IDs. Row-level security follows in
phase 5.

### D3. Two assignments at once can pass the per-driver load limit

**Medium.** `assignableDriver` (`internal/service/shipment.go:618`)
counts the driver's active loads (`CountActiveForDriver`, line 633)
without a lock. Two dispatchers assigning the same driver at the same
moment both see room.

**Fix:** lock the driver's row in the assigning transaction; a test that
assigns twice at once.

### D4. Money is stored in two units

**Low.** Billing keeps whole santim. Shipment charges
(`shipment_charges.amount`) and cargo value (`shipments.cargo_value`) are
`numeric(15,2)` birr. Both clients' plans expect integers in santim.

**Fix:** `bigint` santim columns; the API sends integers everywhere.

### D5. "Every query is scoped by tenant" is not checked

**Medium.** 125 of the 327 queries don't mention `tenant_id`. Most are
global on purpose (queue workers, retention, look-ups by tracking number,
token or code), but nothing tells a deliberate exception from a mistake.

**Fix:** each unscoped query says why (`-- tenant: none, <reason>`), and a
check in CI fails on one that doesn't.

### D6. A delivery's photos can't carry their own time and place

**Medium.** `proof_of_deliveries` keeps `photo_urls text[]` and the
signature inline as text (`signature_data`). AC-021.3 and AC-021.4 ask for
each photo's time and place, and Kiflet/mobile's direct uploads need a
storage key, size and checksum for each file.

**Fix:** a `pod_media` table, a row per file (kind, storage key, size,
MD5, when and where it was taken); signatures stored as files like the
photos.

### D7. No idempotency keys or version checks

**Medium.** Nothing reads `Idempotency-Key` or `If-Match`, or sends an
`ETag`. A create retried after a dropped connection (an integration's, or
a form submitted twice) makes two records; two dispatchers editing one
shipment overwrite each other without knowing. Both clients' plans depend
on both.

**Fix:** an `idempotency_keys` table and a `version` on every editable
record (phase 1), and the headers that use them (phase 2).

### D8. The words for codes are not one catalogue, and sync refusals are vague

**Medium.** The office's words for statuses are `StatusLabel`, in
English; the customer's are in `internal/platform/text`; the driver's
Amharic is in the PWA (`static/driver/text.js`). A refused sync item
carries a generic code (`STALE` or `ERROR`, `sync.go:479` and `487`) and
an English message. The clients expect `{code, label}` in the reader's
language and for the reader's audience, and stable refusal codes
(`cancelled`, `reassigned`, `held_for_review`…).

**Fix:** one catalogue in `internal/platform/text` with the office's, the
customer's and the driver's words for every code, in English and Amharic,
and a test that it is complete; stable refusal codes in the driver API.

### D9. Two costs of the events bus

**Low.** Every shipment event is written to `event_outbox` and published to
`kiflet.events`, which nothing consumes yet. And the subscribers that run
inside the transaction look the company up again, which lengthens every
transaction that changes a shipment, the cause behind D1.

**Fix:** events carry what their subscribers read (phase 1); push
notifications become the outbox's first consumer (phase 3).

## The API

### A1. The clients' contract doesn't exist

**High; it blocks both clients.** Kiflet/web and Kiflet/mobile are planned
against an OpenAPI specification and the `@kiflet/api` package built from
it. Neither exists. Only the public API has a specification
(`internal/web/static/openapi.json`, 8 operations), and the conventions
the clients assume (errors listing every field, the actions a caller may
take, labels for codes, idempotency, versions, request IDs) exist nowhere.

**Fix:** phase 2: one specification, `api/openapi/v1.yaml`, for the one
API, with those conventions; the Go types and the TypeScript package
generated from it; a check for breaking changes in CI.

### A2. The CSRF exemption covers all of `/api/`

**Medium, before the first endpoint the session cookie reaches.**
`internal/web/server.go:136` exempts every `/api/` path from the
cross-origin check. That is harmless while only bearer tokens reach
`/api/`, and wrong as soon as the web app's cookie does.

**Fix:** check every request the session cookie authenticates; exempt
only requests with an `Authorization` header and the providers'
callbacks, which move to `/api/callbacks/*`.

### A3. The plans disagreed

**Low.** The backend's documents asked for a CSRF token header where the
web's relied on Go's cross-origin check; for cursor pagination where the
web's showed numbered pages; for `/api/driver/*` where the PWA uses
`/api/v1/driver/*`. Settled as in [Decided on 2026-11-19](#decided-on-2026-11-19),
and the documents of all three repositories now say the same.

## Privacy and security

### P1. Payment and invoice updates reach every staff member

**Medium.** `internal/service/billing_payments.go:157`, `265` and `443`
publish to the whole company's live channel, so a dispatcher's browser
receives payment and invoice changes only admins may see.

**Fix:** a live message names the roles that may receive it.

### P2. No security linter

**Low.** golangci-lint runs a small set of linters, without gosec.

## Tests

### T1. Most tests go through pages that will be deleted

**High for the migration.** Of the 484 request paths written in
`tests/integration`, 427 are Go pages; most end-to-end tests drive the
pages, or the PWA in Chrome. Deleting a page as Kiflet/web replaces it
would delete the tests of the flows behind it, and most of the coverage
with them.

**Fix:** a page, and its tests, are deleted only once the flows those
tests cover are tested through the modules and the API
(`docs/migration.md`, section 8). The backend's end-to-end tests move to
the API.

### T2. The rules are tested almost only through HTTP

**Medium.** Unit tests cover 6% of `internal/service`. Transitions,
limits, estimated arrivals, alert conditions and billing are checked
through whole requests, which are slow and say little about why
something failed.

**Fix:** each module that moves brings unit tests for its rules and store
tests for its queries.

### T3. The core paths are the least covered

**Medium.** The driver API (62%), proof of delivery (74%), signing in
(72%) and managing people (54%) are the least covered files on the path
from booking to delivery.

### T4. Requirements and tests are not connected

**Low.** 18 of the 49 functional requirements are named in no code or
test, and the end-to-end suite has 9 tests for the E2E guide's 13
sections, so "is FR-xx tested?" has no quick answer.

**Fix:** each test names its requirement; a generated table shows which
have none.

### T5. `TestGatewayFaults` is flaky

**Low.** It fails now and then on CI without a code change.

## Process and operations

### G1. No branch protection

**High.** Lost when the repository moved to the organization; web and
mobile never had it. Nothing stopped a red build reaching `main`.

**Fixed on 2026-11-19:** `main` in all three repositories takes changes
only through pull requests, with no force pushes or deletion, for admins
too; on the backend the four CI jobs must pass on a branch up to date with
`main`. Web and mobile add their CI jobs when they have them. Private
vulnerability reporting, which `SECURITY.md` points to, was off in all
three and is on.

### G2. Nothing is published for the clients

**Medium; it blocks the clients' CI.** There is one tag (`v0.9.0`), images
are built on the server, and nothing goes to a registry. Both clients'
plans run their tests against a published backend image with the demo
data, and build against `@kiflet/api`.

**Fix:** images to `ghcr.io/kiflet/backend` on every merge and a compose
file for the clients' tests (phase 0); the package with the
specification (phase 2).

### G3. Production keeps one copy of each file

**Medium; before the pilot.** `deployments/garage/garage.toml` sets
`replication_factor = 1` for production as for staging; there is no
PgBouncer; the off-site backups are not set up yet (`ROADMAP.md`).

**Fix:** phase 5, and the off-site backups before the pilot starts.

### G4. The plans were out of date

**Low.** `ROADMAP.md` described the repository of 14 November; the
clients' plans were uncommitted.

**Fixed** by this audit's pull requests: the backend's plan and roadmap
rewritten, and the clients' plans committed and brought into line.

## What is solid

- **The schema's discipline:** append-only history and audit log enforced
  by triggers; `client_id` uniqueness for everything a phone sends;
  purges only in `purgeTx`.
- **The sync's write side:** idempotent by `client_id`, a phone's clock
  corrected, the office's decision winning over a stale update, a delivery
  never thrown away (held for review).
- **Background work:** the outbox tables with retry schedules and
  sweepers; RabbitMQ where it helps and a working path without it.
- **The events bus:** subscribers within the transaction for what must
  commit with a change, after it for live updates.
- **The module boundary test,** which keeps moved code from reaching back.
- **Security basics:** webhooks can't reach private addresses, cookies
  are `HttpOnly`, `Secure` and `SameSite`, passwords are bcrypt, logs carry
  no personal data, secrets come from files.
- **Operations:** staging runs production's compose file; the backup is
  restored in the last end-to-end test; Grafana alerts on what matters.

## Scope and method

**Read:** every package under `internal/` and `pkg/`, the migrations and
the queries, the integration and end-to-end tests, `.github/workflows`,
`.golangci.yml` and `deployments/`; in Kiflet/web and Kiflet/mobile,
`docs/architecture.md`, `docs/migration.md` and `docs/design.md`.

**Run:** `make test`; `make test-integration` with coverage over every
package; counts of queries without `tenant_id`, of foreign keys, and of the
paths the tests request.

**Not checked:** behaviour at production's size (the load test has run
only at small scale); the clients, which have no code yet; the providers'
real services.
